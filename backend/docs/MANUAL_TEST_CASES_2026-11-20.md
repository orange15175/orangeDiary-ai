# 统一聊天手工试用用例（2026-11-20）

给产品/自己上手点一遍的清单。每条都是"**输入一句原话 → 看一个明确的地方**"，不需要读代码。

- 执行环境：前端 `http://127.0.0.1:5173` → 登录 → 左侧「AI 助手」（`/ai`）页面。
- 判读入口有两个，任选：
  1. 回答正文（看有没有编造来源、有没有串菜）；
  2. 管理员账号登录后打开 `/admin/ai-traces`，看该轮的 `intent`、`knowledge_domain`、`source_count`、`rerank_state`、`degraded`。
- 结果列留了 `☐`，可以直接在编辑器里勾。**"☐ 通过 / ☐ 不通过"** 由你填。

确定性标记：

| 标记    | 含义                          |
| ----- | --------------------------- |
| **硬** | 规则或数据决定，达不到就是缺陷，可以直接报       |
| 软     | 大模型生成，措辞会变；只看"该不该出现什么"，不抠字眼 |
| 观察    | 当前能力边界，记录实际表现即可，本次不判失败      |

## 0. 三分钟冒烟（先跑这 5 条）

| 编号 | 输入原话          | 预期                                  | 判读点                          | 结果 |
| -- | ------------- | ----------------------------------- | ---------------------------- | -- |
| S1 | `红烧肉怎么做`      | 给出完整做法：焯水→炒糖色→小火炖→收汁；有调料单列和完成判断     | 来源里是菜谱，不是营养文献                | ☐  |
| S2 | `中午吃了200克米饭`  | 弹出饮食记录确认卡，米饭 200g                   | 卡片数值对得上                      | ☐  |
| S3 | `有辣椒、五花肉、鸡腿`  | 推荐 1–3 道这三样能做的菜（宫保鸡丁/辣椒炒五花肉/红烧鸡腿一类） | 不出现清蒸鲈鱼这种无关菜                 | ☐  |
| S4 | 紧接着发 `第二道怎么做` | 讲第二道那道菜的做法，**不重新列一遍推荐**             | 菜名和上一轮的第二道一致                 | ☐  |
| S5 | `今天消耗了多少大卡`   | 正常回答消耗/汇总，**不弹**"跑了多久"的运动记录卡        | 没有 `confirm_exercise_record` | ☐  |

5 条全过，说明意图分流、cooking 域、多轮补全、记录卡四条主链路都在。

## B. 菜谱问答（cooking 域 18 道，抽 8 道）

预期统一为：给出该菜的分步做法，包含**主料用量、调料、火候/时间、完成判断**四项里的至少三项；来源是菜谱，**不能**说成"权威来源/文献表明"。菜谱是项目整理的通用做法，措辞上不应假装有出处。

| 编号 | 输入原话      | 额外检查点                             | 结果 |
| -- | --------- | --------------------------------- | -- |
| B1 | `宫保鸡丁怎么做` | 调料单列（生抽/醋/糖/料酒/淀粉）；花椒干辣椒小火；花生米最后放 | ☐  |
| B2 | `红烧肉怎么做`  | 炒糖色、小火慢炖、收汁判断；参考人数 2–4 人          | ☐  |
| B3 | `番茄炒蛋怎么做` | 先炒蛋盛出、再下番茄回锅；不要变成"番茄鸡蛋汤"          | ☐  |
| B4 | `麻婆豆腐怎么做` | 豆腐先处理不易碎、分次勾芡                     | ☐  |
| B5 | `清蒸鲈鱼怎么做` | 蒸制时间与"虚蒸/焖"；时间只按资料说，资料没写不要硬编精确分钟  | ☐  |
| B6 | `凉拌黄瓜怎么做` | 拍/腌出水、蒜醋调味                        | ☐  |
| B7 | `香菇滑鸡怎么做` | 香菇泡发水利用、蒸或焖                       | ☐  |
| B8 | `醋溜白菜怎么做` | 大火快炒、醋分两次                         | ☐  |

对照检查（同一条回答里看）：**不应**把 3 道不相干的菜凑成"你可以做这些"——检索不到就只答检索到的。

## C. 多轮追问（7 条）

这一组要**按顺序连着发**，前一条是后一条的上下文。

| 编号 | 输入原话                       | 预期                   | 判读点                 | 结果 |
| -- | -------------------------- | -------------------- | ------------------- | -- |
| C1 | `有辣椒、五花肉、鸡腿`               | 推荐 1–3 道             | 候选都能用上给的食材          | ☐  |
| C2 | `第二道怎么做`                   | 讲第二道的完整做法            | 不重复列表；菜名对得上 C1      | ☐  |
| C3 | `不放辣`                      | 沿用同一道菜给调整（去干辣椒，花椒可留） | 不换菜                 | ☐  |
| C4 | `没有生抽了怎么办`                 | 给替代（老抽+盐，颜色会深）       | 继续同一道菜，不换菜          | ☐  |
| C5 | `就做第一道，两个人吃`               | 回到第一道，按 2 人份给量       | 人数进入用量，不是只嘴上答应      | ☐  |
| C6 | `刚才那道菜要多少盐`                | 能指代到上文菜名             | 不反问"哪道菜"（除非真的跨了很多轮） | ☐  |
| C7 | 新话题 `红烧肉怎么做` 之后再问 `第二道怎么做` | 以最新一轮的候选为准           | 不混用 C1 的旧列表         | ☐  |

## D. 只给食材 / 缺调料（6 条）

| -- | -------------- | ------------------ | -- |
| D1 | `我只有鸡蛋和番茄`     | 推荐番茄炒蛋（给做法，不是只报菜名） | ☐  |

## E. 饮食记录（7 条）

| 编号 | 输入原话               | 预期                      | 判读点                      | 结果 |
| -- | ------------------ | ----------------------- | ------------------------ | -- |
| E1 | `中午吃了200克米饭`       | 记录卡：米饭 200g             | 数值原样                     | ☐  |
| E2 | `中午吃了两个鸡蛋`         | 记录卡：鸡蛋 100g             | **不反问克数**（食物库有"个=50g"换算） | ☐  |
| E3 | `中午吃了两个鸡蛋和一碗米饭`    | 一张卡两项：鸡蛋 100g + 米饭 150g | 两项都进卡                    | ☐  |
| E4 | `中午吃了一个苹果`         | 若食物库没有"个"的换算 → **反问克数** | 反问是预期，不是缺陷               | ☐  |
| E5 | `晚上吃了200克米饭，鸡腿怎么做` | 先出记录卡，**再**给鸡腿做法        | 复合消息不能只回"请核对记录卡"         | ☐  |
| E6 | `我吃了饭`             | 反问份量/克数，不出卡             | 缺数量不猜                    | ☐  |
| E7 | `今天吃了多少大卡`         | 汇总回答                    | 不新增记录卡                   | ☐  |

E2/E3 的克数来自食物库"常用份量"，不是模型估算；数字对不上就是换算链断了。

## H. 知识域隔离与降级（5 条）

| 编号 | 操作                                 | 预期                                                  | 结果 |
| -- | ---------------------------------- | --------------------------------------------------- | -- |
| H1 | 问 `每天吃多少盐合适`                       | 来源是营养文献（nutrition 域），**不召回菜谱**                      | ☐  |
| H2 | 问 `红烧肉怎么做`                         | 来源是菜谱（cooking 域），**不召回营养文献**                        | ☐  |
| H3 | 打开 `/admin/ai-traces`              | H1 那轮 `knowledge_domain=nutrition`，H2 那轮 `=cooking` | ☐  |
| H4 | 停掉 Ollama（`ollama serve` 的窗口关掉）后提问 | 有"检索降级/暂时不可用"的提示，**不是**"知识库里没有这份资料"，也不是 500         | ☐  |
| H5 | 重新起 Ollama 后提问                     | 恢复为正常检索，不用重启后端                                      | ☐  |

H4/H5 的区别是本次重点：`unavailable`（服务挂了）和 `no_evidence`（确实没资料）不能混成一句"没有相关资料"。

## 已知边界（遇到这些不算缺陷）

1. **菜谱只有 18 道 + 1 篇搭配经验**（宫保鸡丁、红烧肉、番茄炒蛋、麻婆豆腐、清蒸鲈鱼、可乐鸡翅、红烧鸡腿、葱爆牛肉、蒜蓉西兰花、蒜香茄子、西红柿鸡蛋汤、辣椒炒五花肉、醋溜白菜、青椒土豆丝、韭菜炒鸡蛋、香菇滑鸡、凉拌黄瓜、家常豆腐）。库外菜只能给通用建议并注明。
2. **追问改写是概率性的**：改写失败会自动退回"原句 → 已确认菜名"再检索，所以追问第三条以后偶尔会答偏，属当前已知问题，不是每次都必中。
3. **份量换算只认食物库已维护的"常用份量"**（目前鸡蛋/番茄/土豆/葱/米饭/黄瓜这类）。没维护的食物会反问克数，这是设计，不是漏做。
4. **精确温度与分钟只来自资料**。资料没写，模型应该给"看到什么程度算熟"这类判断，而不是编一个数字。看到硬编的精确数值反而是问题。
5. **字数上限 4000**（与 Java 版一致），超了直接 400。

## 出问题怎么记

一条记录带四项，足够定位：

1. 原话（连标点）+ 是第几轮；
2. 回答里错在哪（截图或复制那一段）；
3. `/admin/ai-traces` 里该轮的 `intent` / `knowledge_domain` / `source_count` / `degraded`；
4. 后端日志里同一 `traceId` 的行。

不想开前端时，可以直接打接口复现：

```sh
# 1) 登录拿 token
TOKEN=$(curl -s -X POST http://127.0.0.1:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"account":"<邮箱或手机号>","password":"<密码>"}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['data']['token'])")

# 2) 发一句（非流式，方便看完整 JSON）
curl -s -X POST http://127.0.0.1:8000/api/ai/chat \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"message":"有辣椒、五花肉、鸡腿"}' | python -m json.tool

# 3) 追问必须在同一会话里接着发（服务端按账号默认会话续）
curl -s -X POST http://127.0.0.1:8000/api/ai/chat \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"message":"第二道怎么做"}' | python -m json.tool
```

看 JSON 里这几个键：`reply`、`action`、`recordPreview`、`exercisePreview`、`sources`、`knowledgeStatus`。

前置检查（跑之前 30 秒确认）：

```sh
curl -s http://127.0.0.1:8000/ready      # {"business":"ready"}
docker ps --format '{{.Names}}\t{{.Status}}' | grep -E 'mysql|redis|qdrant|minio'
```

后端启动日志里要出现 `检索资源加载完成：168 片段，32 篇文档`，且 Ollama 在跑；否则第一条问题会超时或降级，别把环境问题记成业务缺陷。
