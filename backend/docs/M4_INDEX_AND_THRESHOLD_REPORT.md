## 二、索引 v3 的效果

同一评估集、同一门槛（0.60 / 12.0）下对比 v2 与 v3：

| 模式 | 指标 | v2 | v3 | 变化 |
|---|---|---|---|---|
| 混合 RRF | 文档命中 | 96.43% | 96.43% | 0 |
| 混合 RRF | 证据命中 | 92.86% | 92.86% | 0 |
| 混合 RRF | MRR | 0.9107 | **0.9286** | +1.8pp |
| 仅 BM25 | 文档命中 | 92.86% | **96.43%** | +3.6pp |
| 仅 BM25 | 证据命中 | 85.71% | **89.29%** | +3.6pp |
| 仅向量 | 文档命中 | 92.86% | 92.86% | 0 |

结论要说得直白：**标题入索引对关键词通道确实有提升（+3.6pp），对混合模式只体现在 MRR（+1.8pp）**——因为向量通道本来就能召回这些文档，标题带来的增量被融合稀释了。消融时看到的 +3.6pp 是 BM25 单通道的数字，不能直接当成端到端收益，这一点在 M3 报告里我写得偏乐观，这里更正。

v3 索引状态：13 篇 / 144 片段 / 1024 维 / 0 错误；集合 `orange_diary_knowledge_v3`，v1、v2 均保留。

## 三、最关键的发现在证据门槛，不在索引

把负例从 6 道扩到 20 道后，原门槛（0.55 / 6.0）暴露了严重问题：

| 配置 | 文档命中 | 证据命中 | 可答召回 | 负例误答 | 判定准确率 |
|---|---|---|---|---|---|
| v3 + 旧门槛 0.55/6.0 | 100% | 96.43% | 100% | **8/20（40%）** | 83.33% |
| v3 + 新门槛 0.60/12.0 | 96.43% | 92.86% | 96.43% | **0/20（0%）** | 97.92% |

**旧门槛下混合模式比单通道更差**（向量 5/20、BM25 5/20、混合 8/20）。原因是证据过滤用的是"或"逻辑：只要 BM25 分数 ≥ 6.0 就放行，于是一个零星词命中就能把无关问题救活。这是融合设计里的真实缺陷，不是阈值调小了的问题。

改法与依据（分数分布实测，v3 索引）：

- 正例首位向量分最低 **0.554**（烤红薯西瓜 GI），次低 0.592（代糖减肥）
- 负例首位向量分最高 **0.581**（孩子挑食补维生素）、0.572（胰岛素）、0.572（脂肪肝）
- 两者重叠 → **单靠向量阈值不可能分开**，调高到 0.62 就开始误杀正例

因此改为两级门槛：`向量 ≥ 0.60` **或** `关键词 ≥ 12.0`（负例 BM25 最高只有 8.4，正例被救回的烤红薯是 16.5，两侧都有余量）。

代价必须写明：**「用代糖能帮助减肥吗」被误拒**。它的向量分 0.598、BM25 6.7，与负例「孩子挑食需要维生素补充剂」的 0.581 / 8.4 几乎不可分。这是当前信号下的固有上限——真正的解法是 rerank（对 query-passage 做交互打分，而不是比共享词或多向量余弦），不是继续拧阈值。

## 四、负例拆分：两类问题的责任层不同

| 模式 | 完全无关 (14) | 需专业判断 (6) |
|---|---|---|
| 仅向量 | 0/14 | 0/6 |
| 仅 BM25 | 3/14 | 2/6 |
| 混合 RRF | **0/14** | **0/6** |

"需专业判断"指用药、胰岛素、治疗方案、抗凝药饮食禁忌这类问题。它们在检索层能命中同主题资料（例如"我血压高吃什么药"命中减盐内容），**检索层无法判定该不该答**。这类必须由意图层（`out_of_scope`）和提示词层的边界兜住，不能指望检索阈值。本轮的 0/6 只是说明"证据门槛没有再放水"，不代表回答安全——生成侧的拒答约束仍待端到端验证。

## 五、修掉的两个真问题

### 5.1 配置默认值漂移（会被线上真实触发）

改完 `Settings.rag_min_score = 0.60` 后启动服务实测，接口仍然放行 0.598 的查询——因为 `from_env()` 里独立写着 `os.getenv("RAG_MIN_SCORE", "0.55")`，字段默认值根本没生效。同样的漂移还存在于 `rag_collection` / `rag_index_version`（字段是 v3，环境读取默认是 v2）。

修法：默认值收敛为模块常量，字段与环境读取共用一份，并加注释说明为什么不再各写一份。这类问题不改的话，"改了配置没生效"会在联调阶段浪费大量时间。

### 5.2 增量索引漏掉算法升级

原先"是否跳过"只看文档内容哈希和文档版本，切块或索引策略变了也不会重建，新旧片段会混在同一集合里。现在加入 `chunker_version` 与 `index_text_version` 比对，任一变化即重建；新增 4 项测试覆盖三个方向（未变跳过、切块版本变、索引文本版本变、内容变）。
