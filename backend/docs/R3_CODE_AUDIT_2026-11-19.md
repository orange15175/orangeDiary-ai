## 代码检查确认的其他缺口

1. **规划实质能力不足**：`_pick` 按列表顺序去重，不按营养匹配/预算/偏好评分；`prefer_available` 与 `allow_purchase` 没有优先使用库存的排序区别。`dislikes`、菜系偏好已存但未用于候选选择。份数按热量四舍五入后夹在1–3之间，没有独立检查最终一天的热量、蛋白质等是否满足目标。CP-SAT 与独立验证器均需补，不是简单换一个算法名。
2. **动态调整还没有理解实际变化**：`revise` 仅把 `reason/event` 存入快照，重新选餐时不使用它们；未根据聚餐摄入、缺货、加班时间等结构化事实改变约束。它重新读取偏好，而非完整继承原计划请求约束，原请求指定的过敏/设备条件可能在调整时丢失。
3. **库存生命周期不闭环**：采纳新版本会新增预留，但没有释放旧版预留；标记已完成不扣减食材、不释放预留。核对和采购可用量未扣除其他预留；核对/采购没有统一处理 kg/g/个。并发采纳、跨版本过期冲突及重复请求参数冲突需补专门测试，当前不可据顺序冒烟宣称安全。
4. **未知数据有被误当完整的风险**：食谱营养按已知食材累加，coverage 主要代表克重/食材映射，不是每个营养项完整度。缺某食材或某营养项时，仍可能返回部分合计；规划只看热量是否非空就计作已知，需明确 partial/unknown，防止低估摄入。采购需求遇未映射食材或未知克重直接跳过，未完整保留待核对需求。
5. **报价不是填个 key 即可**：`build_price_provider()` 对所有配置都回落 `UnavailablePriceProvider`。`ShoppingService.build_list` 的 knownSubtotal 恒 null、budgetStatus 恒 unverified；接供应商后还要实现单位价格、规格/包装、地区/时间、区间汇总、缺价覆盖和预算核验。
6. **交互仍有断点**：偏好保存、家中食材维护、实际饮食观察的客户端API已写，但无对应完整页面调用；调整页面需要手填计划ID，只弹生成成功，不展示差异/采纳；已有计划列表不能打开详情继续核对；复盘页面不传 withDraftPlan，下周草稿引用只显示文本。AI聊天现有工具仍只有今日汇总、饮食、档案，尚未统一路由到厨师/计划/采购/复盘。
7. **权限边界需补测**：`AdjustmentService.resolve` 校验观察归属，但没有校验所关联的每条正式饮食记录归属和有效性。不能让用户关联别人的记录；该项为静态代码发现，本轮未操作真实他人数据。
8. **清单口径需纠正**：执行清单在“完成”下同时承认预算/CP-SAT等缺失，且声称预留/扣减/补偿已完成，与实际实现不符；IMPLEMENTATION_STATUS 开头又仍写无R3模块、schema0007，已过时。审计时应以当前代码和测试行为为准。

## 推荐执行顺序与可检查的验收结果

### 第一步：修正确性与权限，不需要新数据或供应商

修复上表6项，以及过期版本/预留释放、扣减/撤销补偿、原计划约束继承、记录关联归属。补前后端契约和异常场景回归。验收：三餐不能缺餐仍OK；库存不超分配；核对按钮真正成功；购买/撤销库存回到正确值；七天草稿确为21餐或明确不可行；人数影响实际用量。

### 第二步：完成用户能持续走通的文字版流程

补偏好（过敏/忌口/设备/时间/预算）、食材维护、观察记录、计划详情、差异草稿展示/采纳与采购重算入口；先做页面之间的完整串接，再把已授权的业务请求接入同一AI助手。草稿创建与采纳分离，禁止模型静默写入。验收：用户不填内部ID也能从做饭→规划→核对→采购→记录→调整→复盘继续下一周。

### 第三步：补数据质量与规划引擎

以现有2158条食物数据为基础，整理食谱来源/使用许可、食材ID、克重、基础份数、设备/时间/餐次/过敏标签；补可食部、生熟和单位转换。保留样例标签，正式食谱按设计至少60、目标100道，并以约束覆盖证明够用，不能只凑数量。营养目标复用现有公式，但加入来源、版本、适用边界、用户自定目标以及经审阅的营养范围。实现CP-SAT、独立验证、无解/超时分类。验收：7天21餐及代表性过敏/设备/时间/营养组合通过；未知不得被当成满足约束。

### 第四步：真实图片/价格能力与复盘改进

接图片Provider，照片先出识别草稿，用户确认后再变事实；选择有地区/规格/时点/来源的真实价格渠道，完成预算计算；复盘先算可复核事实，再由模型解释，反馈需实际影响下一周草稿。验收：图片识别错误可改、缺价仍未验证、严格预算有可追溯计算、反馈改变选餐且旧计划采纳前不变。

### 第五步：完整验收与稳定性

用独立测试账号和数据库验证整个周期，覆盖7天21餐、缺食材/未知数量、预算不足、聚餐/加班、重复点击、并发采纳、补记后报告更新、重启恢复与跨账号访问。长任务及外部调用按原设计补恢复/预算/超时能力。真实模型/图片/价格效果另记实测证据；不能以页面能打开或样例测试通过代替验收。

## 需要补充或决定的材料

- 开发者可继续完成：上述修复、接口/页面串接、求解器、数据导入/校验工具、食谱整理，不应一概要求用户自行提供100道菜。
- 食谱资源：确定可用来源和许可，允许开发者整理；有现成自有食谱可优先提供。营养值须关联基础食物或可靠来源，不能由模型编造填满。
- 营养策略：确认面向普通成人的适用范围、采用的营养依据和可配置目标规则；未审阅部分明确标实验/未知，不以现有固定热量修正代替普适营养策略。
- 真实图片：可用模型、兼容接口、凭证及少量代表性测试图片；凭证经本地配置提供，不写入文档。
- 真实价格：目标城市、渠道、价格获取方式/凭证，预算是否含配送。缺少供应商时可先支持用户手填参考单价/实付，并标明来源；不冒充联网报价。
- 用户验收：确定最关心的几条具体场景（如一个人、7天、预算、忌口、设备、已有食材），据此生成可重复的验收表。
